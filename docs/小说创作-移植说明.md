# 「AI 写小说」：从绘梦移植的说明

> 对应工具：侧栏「小说创作 → AI 写小说」
> 相关文件：`src/services/novelService.js`、`src/engine/novelGates.mjs`、`src/assets/novelPrompts.js`、`src/repo/novelRepo.js`、`public/views/novel.js`

## 一、原项目的「写一本书」是怎么串起来的

绘梦把长篇拆成「技能包 + 上下文装配 + 流水线 + 量化门」四层（见 `docs/去AI味-移植说明.md` 第一节）。写书这条链路在它那里是两条流水线：

| 流水线 | 步骤 | 产出 |
| --- | --- | --- |
| `create-book.json` | 立项 → 人物 → 世界观 → 7 列章纲 → 伏笔台账 | 一本书的设定与结构 |
| `write-chapter.json` | L0 写前锚定 → 正文 → L1 量化扫描(≤55) → 红队审查 → 去 AI 味改写 → 复扫定档(≤40) → 落盘 | 一章正文 + 扫描表 + 修改记录 |

关键设计（移植时被保留下来）：
1. **写之前先有约束**：人物有欲望/缺陷/语言指纹，世界规则带代价，章纲每章只允许一个核心事件。
2. **每章都过量化门**：不是写完再整体审，而是一章一章过。
3. **门禁不过不是报错，而是带诊断重写**。

## 二、移植成什么样

```
立项(建书)  →  设定集(bible)  →  章纲与伏笔(outline)  →  逐章正文(chapter)  →  导出全书
   表单         POST .../bible     POST .../outline        POST .../chapter      GET .../export
```

四个动作是**分开的端点**：写到第 40 章时只改一章，不该被迫重跑整条链（也白花钱）。

### 数据模型（一本一文件，`data/novel-<id>.json`）

```js
{
  id, title, genre, logline, audience, tone, forbidden,
  targetWords, wordsPerChapter,
  bible:   { promise:{sellingPoint,theme,ending}, characters:[{name,role,want,flaw,voice,arc}], world:[{rule,cost,bound}] },
  outline: { volumes:[], chapters:[{index,title,goal,conflict,turn,hook,characters}], foreshadow:[{id,content,plantAt,payoffAt,tier}] },
  chapters:[{ index,title,text,words,scan:{score,grade},gates:[],ok,error }]
}
```

与绘梦的差异：它用 Markdown 目录树（`novel.md` / `outline.md` / `chapters/vol-1/ch-001.md`），本项目统一用 JSON 仓库 + 索引。原因是本项目已有「作品库」的 JSON 形态，再引一套 Markdown 文件树会让「作品」有两个家。**代价**是手改正文要去 `data/` 里找 JSON，不如 Markdown 直观——但导出功能补上了这一环。

### 门禁（确定性，`src/engine/novelGates.mjs`）

**设定门 8 道**（写正文前跑，避免「写了十万字才发现大纲不成立」）：

| 门 | 在数什么 |
| --- | --- |
| 书名 | 2–14 字 |
| 一句话故事 | 12–90 字，且看得出冲突（转折词/想要/阻力） |
| 人物档案 | ≥3 人，且 ≥2 人写清了「要什么」与「缺什么」 |
| 世界观规则 | ≥3 条，≥60% 带代价或边界 |
| 篇幅匹配 | 章数 × 单章字数 与目标字数相差 ≤25% |
| 章纲要素 | 每章都有 目标/冲突/钩子 |
| 伏笔台账 | ≥2 条，且每条 回收章 > 埋设章、不越界 |
| 结局方向 | 非空（先定终点再写开头） |

**单章门 6 道**：

| 门 | 口径 |
| --- | --- |
| 本章字数 | 目标 ±25% |
| 章末钩子 | 末段有悬念信号，或末段 ≤60 字的短句收尾（长段收尾通常是总结） |
| 对话密度 | ≥5%（「」与双引号都认） |
| 与上一章承接 | 开头前 8 个字不与上一章相同 |
| AI 痕迹 | 复用 13 维扫描，初稿线 55、定稿线 40 |
| 结尾不总结 | 末段不出现「终于明白 / 从此 / 他知道…」 |

### 提示词（`src/assets/novelPrompts.js`）

- 人物/世界/承诺 → JSON（门禁要数得准，必须结构化）
- 章纲 + 伏笔 + 分卷 → JSON
- 正文 → Markdown 纯文本（读者看的是它）
- 去 AI 味纪律**不在这里另写一份**，直接引用 `assets/deaiRules.js` 的六项诊断/减法/加法，两处共用一份口径。

## 二·五、第二轮迭代：从「墨笔 AI 写作台」取来的连续性记忆

第一版小说链路只有一个短板最要命：**写到第十章以后开始记不住前面**。
当时只给模型「上一章结尾 600 字」，谁出过场、埋了什么伏笔、过了多久全靠它自己猜。
「墨笔 AI 写作台」的 `memory.js` 正好解决这件事，于是把这一块搬过来做了第二版。

**搬来的（纯规则，不花额度）**：`src/engine/novelMemory.mjs`

| 能力 | 原版做法 | 本项目的改动 |
| --- | --- | --- |
| 本章要点 | 按动作动词/数字/位置打分取段落首句 | 原样保留 |
| 关键词 | 2–4 字片段 + 英文整词按频次 | 原样保留 |
| 人物 | 强信号（场次头/行内 cue）+ 弱信号（X说/道/问）按门槛合并 | **改为「按人物表点名」优先**：书里本来就有确定的人物表，精确匹配比正则猜准得多 |
| 地点 / 伏笔句 / 时间线 | 正则 | 原样保留 |
| 全书脉络 | 逐章要点汇总 + 去重的人物/地点/伏笔池 | 原样保留 |
| 注入提示词 | `memoryToPrompt` 拼「全书脉络/已出场人物/待回收伏笔」 | 增加「本章应回收」标记与「上一章发生了什么」 |

**为什么人物抽取要改**：实测原版的弱信号在 2–3 字窗口里不稳定——「照在沈砚的脸上」抽出「在沈砚」、
「沈砚问：」抽出「沈砚问」、「守夜人没答」抽出「守夜人没」。碎片频次被拆散，最后一整批被门槛滤掉，
人物表直接为空。改成「先用人物表点名，再用结构化线索补充新人名」，既准又不会漏；
只有书里没有人物表时才退回弱信号（门槛提到 3 次，宁缺勿滥）。

**新增的三件东西**（原版没有的）：

1. **伏笔状态机**：`planted`（埋设章写出）→ `paid`（回收章正文提到）／`due`（正好到回收章但没提到，待人工确认）／`overdue`（过了回收章还没提）。
   判定用的是「伏笔内容的 2–4 字片段是否出现在正文里」——只判有没有提，不判收得好不好。
2. **人工确认出口**：模型换了说法时关键词判不出来，伏笔标签可以点一下直接标为已回收（`confirmForeshadow`）。
3. **连续性提示**（不硬拦）：本章出现设定与大纲里没有的新人名、或有伏笔已逾期，写章返回里带 `advisories`，界面黄条提示。

**没有搬的**：墨笔的「平台预审（敏感词/风险主题扫描）」——那需要维护一套词表且误判率高，
本项目暂时不做；它的六条创作路径、编辑器、桌面壳也不适合本项目形态。

## 三、与原版的取舍

| 原版能力 | 本项目 | 原因 |
| --- | --- | --- |
| 50 个技能包可替换 | 4 个固定动作 | 本项目工具是「代码 + 固定提示词」，做技能热插拔会变成第二套心智模型 |
| 七阶段续写引擎（`continue_engine.js`） | 逐章写作 + 单章重写 | 七阶段依赖整本书的运行态台账，收益不抵复杂度；本章重写已能覆盖「改一章」的真实需求 |
| 红队审查技能（`forge.redteam`） | 未移植 | 它产出的是「自我举证清单」，与确定性门重叠；先用门把硬指标卡住更划算 |
| 小说/剧本两种体裁 | 小说（长篇），剧本走已有的「AI 剧本生成」 | 同一产品里两条链路各管一种体裁，不混在一个按钮里 |

## 四、接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/novels` | 书目列表（进度、字数、平均 AI 痕迹） |
| POST | `/api/novels` | 立项建书 |
| GET | `/api/novels/:id` | 书 + 8 道设定门 + 就绪度 |
| POST | `/api/novels/:id/bible` | 生成设定集 |
| POST | `/api/novels/:id/outline` | 生成章纲 + 伏笔 + 分卷 |
| POST | `/api/novels/:id/chapter` | `{ index }` 写（或重写）一章；返回含 `memory`、`advisories` |
| POST | `/api/novels/:id/foreshadow` | `{ id }` 人工确认某条伏笔已回收 |
| GET | `/api/novels/:id/export` | 导出全书 Markdown |
| DELETE | `/api/novels/:id` | 删书（只摘索引，正文文件保留可找回） |

## 五、怎么验证

```bash
node scripts/selftest.mjs     # 小说门 10 项 + 连续性记忆 11 项（人物/要点/伏笔状态机/提示词拼装）
node scripts/featuretest.mjs  # 12 项接口测试（建书/设定/章纲/正文/导出/删除 + 6 个边界）
node scripts/rendercheck.mjs  # 视图三态：空书目 / 新建表单 / 完整工作台（含记忆面板）
```
