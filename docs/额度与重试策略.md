# 调用额度与重试策略

**日期**：2026-10-27
**范围**：LLM 调用的失败归因、重试策略、命中率目标、额度监控

---

## 一、诊断：额度花在哪、为什么反复失败

数据来自应用自己的账本 `data/llm-usage.json`（453 次调用 / 320 万 token / 成功率 74%）。

### 1.1 消耗分布（按功能）

| 功能 | 调用 | 失败 | token | 占比 | 平均耗时 |
| --- | --- | --- | --- | --- | --- |
| 拆分镜 `shots` | 268 | 89 | 2,157,292 | **67.4%** | 48s |
| 分集大纲 `epoutline` | 26 | 4 | 242,609 | 7.6% | 53s |
| 分集正文 `epscript` | 23 | 0 | 185,510 | 5.8% | 21s |
| 剧本正文 `script` | 38 | 2 | 175,421 | 5.5% | 17s |
| 剧本评估 `eval` | 16 | 1 | 172,069 | 5.4% | 39s |
| 梗概人设 `story` | 45 | **21**（47%） | 170,631 | 5.3% | 37s |
| 大纲 `outline` | 28 | 3 | 83,058 | 2.6% | 13s |
| 抓取 `crawl` | 9 | 0 | 11,831 | 0.4% | 7s |

**结论一：拆分镜一个功能吃掉三分之二的额度。**

原因是结构性的，不是 bug：

- 每拆一集 = 一次完整调用：输入带本集正文 + 大纲 + 人物编号；输出是 15 秒段 + 子镜头 + 每段一条摄制单 → **输出极长**（平均 48 秒）
- 门禁不过要**带诊断重修一轮** → 失败一次就再来一遍
- 用户侧一次设 60 集 → 一次点击就是 60 次调用起步

### 1.2 失败归因（最近 100 条聚类）

| 失败原因 | 次数 | 该不该重试 | 旧代码的行为 |
| --- | --- | --- | --- |
| 模型调用超时（120s） | 17（50%） | **不该原样重试**——同一份超大输入重试，大概率再超时 | 重试 3 次 → 白等约 6 分钟 |
| Insufficient Balance（402） | 16 | **绝对不该**——余额不足重试一万次也不会好 | 重试 3 次 → 纯浪费 |
| system cpu overloaded（5xx） | 1 | 该 | 重试（合理） |
| fetch failed | 1 | 该（一次） | 重试（合理） |

**结论二：120 次失败里有 33 次（超时 + 余额）是"规则性浪费"，占总失败的四分之一以上。**

### 1.3 根因：重试是无条件的

`src/agent/llm.js` 旧实现：

```js
for (let i = 1; i <= max; i += 1) {
  try { return loadJsonLike(await complete({ system, user })); }
  catch (err) { lastErr = err; /* ← 不看错误类型，直接下一次 */ }
}
```

而错误对象里其实**已经带了 `status` 和 `transient`**（由 `llmClient.js` 放进 `err.details`），策略层完全没使用。

另一个隐性放大：`record()` 在 `complete()` 里调用，**每次重试都记一次调用**。所以"268 次调用"里混着重试，真实业务调用数要少得多。

## 二、设计的策略

新增 `src/agent/retryPolicy.js`，把"什么错该重试"从调用链里抽成纯函数（可单测、可 review）。

### 2.1 错误分类表

| 类型 | 判定依据 | 重试 | 上限 | 给用户的建议 |
| --- | --- | --- | --- | --- |
| `balance` | 402 / "Insufficient Balance" | **否** | 1 | 去服务商后台充值，重试不会恢复额度 |
| `auth` | 401 / 403 | **否** | 1 | 检查 Key 与 Base URL 是否匹配 |
| `model` | 404 | **否** | 1 | 点「拉取模型列表」选真实模型名 |
| `request` | 400 / 413 / 422 | **否** | 1 | 输入过长或参数越界，缩短再试 |
| `rate` | 429 | 是 | 2 | 已自动退避 |
| `server` | ≥500 / 过载 | 是 | 2 | 已退避，稍后再来 |
| `timeout` | AbortError / 超时 | 是（**仅 1 次**） | 2 | 缩短输入或调大超时 |
| `transport` | fetch failed / ECONNRESET | 是 | 2 | 检查网络 |
| `parse` | 输出不是合法 JSON | 是 | 3 | 下一轮自动追加"只输出 JSON"提示 |
| `content` | 只有思维链 / 正文空 | 是 | 2 | 调大最大 Token 或降推理等级 |

**三条设计原则**

1. **配置类错误立刻失败**：余额、Key、模型名、参数——重试改变不了任何东西
2. **超时只补一次**：超时的共同原因是"输入太大"，原样重试是在赌运气
3. **只有可恢复错误才退避重试**：限流、5xx、网络抖动、JSON 没解析出来

### 2.2 退避与抖动

```
rate  : 2000ms → 4000ms（+0~30% 抖动）
其他  : 800ms  → 1600ms（+0~30% 抖动）
上限  : 15000ms
```

固定间隔会让所有客户端在同一秒重试，把限流打成雪崩。抖动是必须的。

### 2.3 提高二次命中：只对解析失败追加修复提示

```js
if (p.kind === ERROR_KIND.PARSE) repairSuffix = '\n\n【上次输出无法解析为 JSON。请只输出一个 JSON 对象，不要任何解释文字、不要 markdown 代码块】';
```

加在 **user 末尾而不是 system**，避免破坏提示词缓存键。

### 2.4 调度层（已具备 + 建议）

| 机制 | 现状 | 说明 |
| --- | --- | --- |
| 串行执行 | ✅ 已有 | 增量生成逐集串行，不会并发打满 |
| 结果缓存 | ✅ 已有 | 拆分镜按 `ep+正文+人物+画风+画幅` 做 sha1 缓存，同参数重跑命中缓存 |
| 断点续跑 | ✅ 已有 | 已完成的集不重写（真模型下每集都花钱） |
| 批量前确认 | ⬜ **建议加** | 拆 60 集前提示"将发起 60 次调用" |
| 熔断 | ⬜ **建议加** | 同任务连续失败 3 次即停本批（`BREAKER_THRESHOLD` 已定义） |
| 日额度闸 | ⬜ **建议加** | 超过日上限直接拒绝，不发请求 |

## 三、命中率：定义、现状、如何到 90%

### 3.1 定义（重要：和"成功率"不是一回事）

| 指标 | 定义 | 说明 |
| --- | --- | --- |
| **命中率** `hitRate` | **第 1 次尝试就成功** / 第 1 次尝试总数 | 反映"一次就能过"的能力，是额度的真实效率 |
| **成功率** `successRate` | 成功 (含重试后) / 全部请求 | 会掩盖重试造成的浪费 |

> 成功率 90% 但命中率 60%，说明一半成功靠重试堆出来——额度在漏，而成功率看不出来。

### 3.2 已实现的度量

`record()` 增加 `attempt` 字段，`totals` 增加 `attempt1Calls` / `attempt1Ok`，`summary()` 输出：

```json
{ "hitRate": 88, "retried": 41, "successRate": 92 }
```

`/api/llm/usage` 直接返回这三个值；「引擎与关于」页新增 **命中率** 与 **重试次数** 两个指标，命中率低于 90% 会高亮。

> 历史数据没有 `attempt` 字段，所以命中率显示 `—`（不是 0）。从本次改动之后的新调用开始累积。

### 3.3 到 90% 的路径

按当前失败结构，改动后预估：

| 失败类型 | 旧行为 | 新行为 | 对命中率的贡献 |
| --- | --- | --- | --- |
| 余额不足 16 次 | 重试 3 次 × 失败 | 1 次即止 | 不再拉低命中率（第一次就失败，但不再放大调用数） |
| 超时 17 次 | 重试 3 次 | 重试 1 次 | 减少 2 次无效等待 |
| JSON 解析 | 无修复提示 | 追加"只输出 JSON" | **二次命中显著提升** |
| 5xx/限流 | 立即重试 | 退避重试 | 重试成功率上升 |

**预计命中率从当前水平提升到 85–92%。** 但要诚实：**90% 不是一个开关能保证的**，它取决于：

1. 输入是否过大（拆分镜单集输入就有 ~40k 字符 → 超时）
2. 网关是否稳定
3. 余额是否充足

所以监控必须常看，低于 90% 要能定位到是哪个任务、哪类错误。

## 四、如何监控

### 4.1 日常看板（无需额外工具）

「引擎与关于 → 模型用量」现在显示 6 个指标：

```
调用次数 | 命中率 | 成功率 | 重试次数 | 总 Token | 平均耗时
```

判断规则：

| 现象 | 含义 | 该做什么 |
| --- | --- | --- |
| 命中率 < 90%，成功率正常 | 重试在替失败兜底 | 看下方"按任务"表，找出失败集中的功能 |
| 命中率低 + 成功率也低 | 真实故障 | 看最近记录的 `error` 字段归因 |
| 重试次数突增 | 网关抖动或限流 | 检查是否与服务商状态公告时间重合 |
| 某任务 token 占比过高 | 该功能输入输出太大 | 拆分镜：减少集数批次；评估：缩短剧本 |

### 4.2 命令行查账（服务在跑时）

```bash
# 命中率与重试
curl -s http://127.0.0.1:8787/api/llm/usage | node -e "
let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{
  const t=JSON.parse(s).totals;
  console.log('命中率',t.hitRate+'%','| 成功率',t.successRate+'%','| 重试',t.retried,'| token',t.tokens);
});"

# 最近失败归因（哪类错误最多）
node -e "
const d=JSON.parse(require('fs').readFileSync('data/llm-usage.json','utf8'));
const f=d.recent.filter(x=>!x.ok);
const m={}; f.forEach(x=>{const k=(x.error||'无').slice(0,30); m[k]=(m[k]||0)+1;});
console.log(Object.entries(m).sort((a,b)=>b[1]-a[1]).slice(0,5));
"

# 按功能看 token 占比
node -e "
const d=JSON.parse(require('fs').readFileSync('data/llm-usage.json','utf8'));
Object.entries(d.byTask).sort((a,b)=>b[1].tokens-a[1].tokens)
  .forEach(([k,v])=>console.log(k.padEnd(12), v.calls+'次', v.tokens+'token', v.failed+'失败'));
"
```

### 4.3 服务端日志（更细）

```bash
journalctl -u miku -f | grep -E "llm\.(retry|giveup)"
```

- `llm.retry`：记录第几次尝试、错误类型、退避时长
- `llm.giveup`：记录为什么放弃（`kind` = balance/auth/model/request 说明是配置问题，不是网络问题）

这一条比命中率更有用：**看到 `giveup kind=balance` 就该去充值，而不是继续点重试。**

### 4.4 账本字段说明（便于自己写报表）

`data/llm-usage.json`

```jsonc
{
  "totals": { "calls":453, "ok":333, "failed":120,
              "attempt1Calls":0, "attempt1Ok":0,      // 本次改动后开始累积
              "promptTokens":1007319, "completionTokens":2191102, "ms":18095768 },
  "byTask":  { "shots": {"calls":268,"ok":179,"failed":89,"tokens":2157292,"ms":12856109} },
  "byModel": { "deepseek-flash": {...} },
  "recent":  [ { "ts":..., "task":"shots", "ok":false, "attempt":2,
                 "error":"模型调用超时，可调大超时或缩短输入" } ]   // 只留最近 100 条
}
```

> 注意：`totals` 里存的是 `promptTokens` / `completionTokens`，**没有 `tokens`**。
> 总 token 由 `summary()` 计算（100.7 万输入 + 219.1 万输出 = 320 万）。直接读文件看到 `tokens` 为 undefined 不是 bug。

## 五、还没做的（下一步）

| 项 | 价值 | 成本 |
| --- | --- | --- |
| **批量前确认**：拆 N 集先提示"N 次调用" | 防误操作烧额度 | 小（前端 confirm） |
| **熔断**：同任务连续失败 3 次停批 | 防"60 集一路烧" | 小（`BREAKER_THRESHOLD` 已留） |
| **日额度闸**：`LLM_DAILY_TOKEN_LIMIT`，超额拒绝 | 硬止损 | 中（需按日聚合 + 中间件） |
| **超时自适应**：输出长度大时自动升超时 | 减少超时失败 | 中 |
| **明细导出**：`recent` 只留 100 条，导出全量 | 对账、追责 | 小（加导出接口） |

## 六、这次改动不能证明什么

- 命中率 90% 是**基于失败结构的推算**，不是实测结果——要等新调用累积后才能验证
- 没有在真实网关跑过（当前无 Key，全程 mock）：分类逻辑用真实错误样例做了单元级验证，但**真实错误消息的措辞可能与我匹配的正则不吻合**（不同网关差异很大），需要上线后看 `llm.giveup` 的 `kind` 是否归类正确
- 历史数据没有 `attempt` 字段，命中率对老数据是 `—`，不会回填
